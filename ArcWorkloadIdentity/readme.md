# ArcWorkloadIdentity

Companion code for [Access Azure Key Vault from a local Kubernetes cluster with Azure Arc workload identity](https://powers-hell.com/2026/08/26/access-azure-key-vault-from-a-local-kubernetes-cluster-with-azure-arc-workload-identity/).

Connects a local Kubernetes cluster to Azure Arc, enables workload identity, and lets a pod
read a secret out of Azure Key Vault without a secret, a certificate or a connection string
anywhere near it.

## Contents

| File | What it does |
| --- | --- |
| `New-ArcWorkloadIdentityLab.ps1` | Builds the whole lab end to end and runs the test pod |
| `Remove-ArcWorkloadIdentityLab.ps1` | Deletes the resource group and the local cluster |
| `serviceAccount.yaml` | Reference copy of the annotated service account |
| `workloadIdentityTest.yaml` | Reference copy of the test pod |

The two YAML files are generated by the setup script from your own values. They are included
here so you can see what they look like without running anything.

## Prerequisites

Software:

- [Docker Desktop](https://www.docker.com/products/docker-desktop/)
- [k3d](https://k3d.io)
- [kubectl](https://kubernetes.io/docs/tasks/tools/)
- [Azure CLI](https://learn.microsoft.com/en-us/cli/azure/install-azure-cli)
- [PowerShell 7](https://learn.microsoft.com/en-us/powershell/scripting/install/installing-powershell-on-windows)

Workload identity on Arc only supports a [specific set of distributions](https://learn.microsoft.com/en-us/azure/azure-arc/kubernetes/workload-identity#prerequisites).
The Kubernetes that ships inside Docker Desktop is not one of them, and neither is kind. That
is what k3d is for.

PowerShell modules:

```powershell
$modules = @("Az.Accounts", "Az.Resources", "Az.ConnectedKubernetes", "Az.ManagedServiceIdentity", "Az.KeyVault")
$modules | ForEach-Object { Install-Module -Name $_ -Force -AllowClobber -Scope CurrentUser }
```

Make sure **Az.ConnectedKubernetes** is up to date. The workload identity switches were only
added fairly recently.

Permissions: Owner on the subscription, or Contributor plus **Role Based Access Control
Administrator**. Creating the role assignment needs `Microsoft.Authorization/roleAssignments/write`,
which Contributor does not include.

## Usage

```powershell
./New-ArcWorkloadIdentityLab.ps1 -TenantId '<tenant-id>' -SubscriptionId '<subscription-id>'
```

When you are finished:

```powershell
./Remove-ArcWorkloadIdentityLab.ps1 -SubscriptionId '<subscription-id>'
```

## If it doesn't work first time

- The issuer URL in the federated credential has to match the OIDC issuer the Arc cluster
  reports. Exactly, trailing slash and all.
- The API server has to actually be signing tokens with that issuer. Check the `iss` claim.
- The subject has to match `system:serviceaccount:<namespace>:<serviceaccountname>`.
- The pod has to use the service account you annotated, not `default`.
- The pod needs the `azure.workload.identity/use: "true"` label, or the webhook ignores it.
- The managed identity needs `Key Vault Secrets User` over the vault, and the vault needs to
  be using RBAC rather than access policies.
- Federated credentials take a moment to propagate. Go and make a coffee, then try again.
